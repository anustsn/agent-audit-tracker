Overview

Which standards and drafts let an auditor answer which agent acted, on whose behalf, with which credential and tool version, and was it allowed?

A public reference for auditors and researchers. It tracks the documents that define audit evidence for AI agent actions: their status and revisions, how they cite each other, and new related drafts, each with its source and the time it was checked. This version is a catalogue: it reports facts from the documents' registries and does not assess the documents, monitor agents or publish findings. The rules are in About, every change is recorded, and errors can be reported.

          How to check a fact
          1. Select a document and note its revision, the time the status was fetched and the source (IETF Datatracker, RFC Editor or GitHub).
          2. Open the registry page or the archived text; for Internet-Drafts and RFCs compare the SHA-256 shown with the text you download.
          3. For a citation, open the Datatracker page of the citing draft; references are listed per revision.
          4. For the history of a fact, see Changes and the commit history of the data files. If something is wrong, report it as a GitHub issue.
          How to re-verify a rating
          1. Select a cell in Specification status and note the revision it was rated at and the text link.
          2. Open the archived text and compare its SHA-256 with the one shown, so you know you are reading the same bytes.
          3. Find the identifiers listed in the cell (and the location, where recorded) and read the definition.
          4. Compare with the rating and the researcher's note. If you disagree, report it as a GitHub issue.
          5. For the history of a rating, see the ratings log below and the commit history of data/fields.json.

            What this tracker covers Researcher classification

            Method

            • Purpose. A research instrument and reference for auditors and researchers. It does not monitor agents and does not publish findings.
            • Maintenance. Maintained by one person. In place of a second reviewer, the rules are stated here, every change is recorded in the data history, and errors can be reported as GitHub issues. The set of tracked areas is fixed; new documents are added only within them, as status-only entries.
            • Three layers. Document facts come from registries (IETF Datatracker, RFC Editor, GitHub) or are recorded by hand with a revision and pointer (data/status.json, data/references.json, data/document_facts.json). Researcher classification covers the evidence questions, ratings, roles, document-type labels, maturity normalisation, coding links, links found by reading and the ratings log (data/fields.json, data/classification.json, data/requirements.json, data/ratings_log.json). Evidence quality is a separate assessment (data/quality.json). The files are never merged.
            • Provenance. The update job records the archive URL and SHA-256 of each Internet-Draft and RFC text, full commit SHAs for repositories, the source commit and workflow run of each build, and the SHA-256 of every curated data file.
            • References are taken from the Datatracker per revision. A citation to a draft that has since been replaced is flagged; it may have been correct when written. Process references (RFC 2119, RFC 8174, BCP 14) are hidden by default and counted.
            • Authority (document type) is shown for context and is never used as a weight.
            • Limits. The tracker covers the documents listed; it does not claim that nothing is missing. Internet-Drafts are work in progress. Nothing here is legal or compliance advice.
            Rules for the researcher's ratings (not published yet)
            • Specification status is rated only after reading, and each column records the revision that was read, the date and, where recorded, who rated it and which sections were read. "Not specified" means the document was read and does not define it; "not reviewed" means nobody has checked. When a newer revision appears, the column is marked re-check rather than silently kept. Cells are never created in advance.
            • Evidence quality. Origin (as specified) and integrity of the record format. "Not established" means the research has not determined it, not that the property is absent. A specified telemetry field is not by itself reliable audit evidence. Requirement levels are document facts and are quoted as the document writes them.
            • Revision check (automatic). For a column marked re-check, the update job compares the revision that was read with the current one and reports changed lines, added or removed section headings, and whether each recorded field identifier still appears or sits in a changed line. This only points to where to read; it does not replace reading.
            • Requirement links in the question view come from the coding in the agent-telemetry-coverage dataset (question → monitoring signal → OWASP requirement unit). Only identifiers are copied. ISO/IEC 27001 and PCI DSS are not coded yet.
            • Best current rating uses only columns rated at the current revision; an older read is shown beside it but not counted.

            Privacy

            • The page sets no cookies, stores nothing in your browser (the theme choice is not remembered), contains no tracking or advertising code, and loads nothing from other servers. A content security policy tells the browser not to load scripts, styles or anything else from elsewhere and not to send data anywhere.
            • Search, filters and exports run in your browser only. Nothing you type is transmitted.
            • The page is hosted on GitHub Pages. GitHub states that when a GitHub Pages site is visited, the visitor's IP address is logged and stored for security purposes (GitHub documentation). The maintainer does not receive these logs.
            • Links to other websites open without telling them which page you came from.
